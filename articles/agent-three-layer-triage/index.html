「AI 說它做完了，可是東西是壞的」｜Agent 排障三層地圖，先修環境再修反饋，流程最後才畫

一支影片拆解了一篇 58 萬瀏覽的長文，講的是同一件事：Agent 不可靠，先別急著怪模型，要先問壞在哪一層。

這篇在講什麼

AI Agent 在測試時很聽話，正式做事就開始出包。真正卡住人的往往不是故障本身，是不知道該從哪裡查起：改提示詞？換模型？加記憶？這篇整理一張排障地圖，把「Agent 不可靠」拆成三個可以分開檢查的層：環境、反饋、流程。看到症狀就知道該查哪一層，不用每次都從頭猜。

適合誰
  • 已經在用 AI 幫忙做事的人，不需要會寫程式
  • 有過「叫它做一件事，它中間自己跑了好幾步」經驗的人，不管那是整理一疊會議紀錄、跑一份報表，還是接了自動化工具
  • 目前還是一問一答的人也可以先收藏，等開始讓它連續做事再回來看
你可以帶走什麼
  • 一張七種症狀的分層對照表，看到症狀直接查該修哪一層
  • 七個可以直接照做的工程紀律，我重新分成五組，可以只挑自己中的那組
  • 一份三步驟的排障清單，文末可直接複製去用

這篇整理自一支影片，出處我會逐句標出來

先把來源交代清楚，免得你讀到一半分不出哪句是誰說的。

這篇整理自一支中文影片。影片作者是「為什麼叫QQ」，他在影片裡自述是從一線工程師的視角來講，內容是拆解 X 上作者 beamnxw 的一篇長文。那篇長文的主題是把 Agent 系統切成三層來排障，截至影片截圖時累積約 58 萬瀏覽、6.5 萬收藏。

Demo 很乖，一上線就失控的六種症狀

［影片作者］影片開頭列了一串狀況，做過 Agent 上線的人應該都眼熟：

  • Agent 跑了一大圈，回報「我做完了」，結果產出物全是壞的。
  • 循環重試二十次，Token 帳單翻三倍，問題還在原地。
  • 換一個會話再打開，它把昨天的進度忘得乾乾淨淨。
  • 你多給它五個工具，它反而開始亂調用。
  • 出了問題去問模型，模型一臉無辜。

［我的整理］如果你手上有在跑的 AI 流程，把上面五條對一遍，通常至少會中兩條。中了不代表你設定得爛，代表你缺一張地圖。

真正卡住人的，是不知道該從哪裡查起

［影片作者］影片作者說，最讓人絕望的不是故障本身，是「故障明明就在那裡，但你根本不知道該從哪兒查起」。要改提示詞？換模型？加記憶？加流程編排？每個方向都有人跳出來推薦框架，每個框架都拍胸脯說自己是終極答案。

［影片作者］他對這篇長文的評價很直白：它沒有發明任何新東西，它給的是一張排障地圖。你的系統由哪幾層組成、每層負責什麼、出現某個具體症狀該去哪一層抓問題。

［影片作者］至於為什麼收藏數這麼高，他的解讀是：大家把它當成一張工程速查表在存，怕以後找不到。

［我的整理］這一點對非工程背景的人特別重要你不需要先變成工程師才能用這張表。你需要的是一個習慣：遇到 AI 出包，先問「壞在哪一層」，再決定要不要動模型。把「模型不夠聰明」當成第一個結論，通常會讓你花錢換模型，然後發現沒有改善。

把 Agent 拆成三層：環境、反饋、流程

［原文］那篇長文的「30 秒版本」核心是三句話。我把原文定義和白話翻譯並排放：

層［原文］定義［我的整理］白話翻譯
Harness Engineering打造模型周圍的機器，負責管「環境」它的工作環境：拿得到什麼工具、看得到什麼資料、有什麼權限、記不記得上一輪
Loop Engineering設計重複的工作反饋循環，負責管「反饋」它怎麼知道自己做對了、什麼時候該停、失敗了怎麼辦
Graph Engineering把工作流的拓撲結構顯式化，包含節點、分支、匯合，負責管「流程」誰先誰後、什麼情況走哪條路、幾條路最後在哪裡合起來

［原文］三層的嵌套關係是：圖跑在 Harness 裡，循環活在圖裡，而 Harness 給循環提供狀態、工具和評估器。

［我的整理］用日常一點的方式理解這個嵌套環境是辦公室，流程是工作規範，反饋是驗收機制。辦公室要先能用，規範才有意義；規範定好了，還是要有人驗收才知道做對沒有。

一個判斷法：把模型拿掉，剩下的都是環境層

［原文］長文給了一個判斷法，影片作者形容它「非常粗暴但極其好用」：

把你架構圖裡的基座模型拿掉，剩下的基本全是 Harness。System Prompt、工具定義、記憶、沙箱、權限、日誌、上下文壓縮、路由，全部都算。

［我的整理］換成你的日常：你在 ChatGPT 或 Claude 裡設定的自訂指令、你掛上去的連接器、你給它讀的資料夾、你允許它動的檔案範圍、你留給它的進度筆記，全部都是環境層。這一層通常是你自己搭的，也通常是最少人檢查的。

同一個模型，兩個團隊做出天差地別的結果

［原文］長文有一個觀察：兩個團隊用同一個基座模型，產出可以天差地別。一邊提供了乾淨的工具、穩定的工作區、嚴格受限的權限和完全可觀測的狀態；另一邊只有模糊的提示詞和很不可靠的 API 封裝。

［影片作者］影片作者把這件事翻成一句話：智能水準差不多，但「打工條件」完全不同。他接著補了一句判斷：硬換更強的大模型，也救不了爛透了的工程環境。

［我的整理］這裡藏著一個容易忽略的錯配市面上賣得最兇、講得最熱的是流程編排那一層（各種框架），但依照下面那張症狀表，一般人日常會踩到的問題，絕大多數落在環境層和反饋層。買一個流程編排框架來修環境層的病，錢花了病還在。

七種症狀各歸哪一層：可以截圖的對照表

［影片作者］這是影片作者認為「光衝這一條就值回票價」的部分，他在念到這裡時還提醒觀眾可以準備截圖。［原文］表格內容出自長文：

症狀歸哪一層該去查什麼
Agent 沒辦法安全存取資料或工具環境（Harness）工具契約、權限控制、沙箱隔離、上下文注入
跨會話就忘記進度環境（Harness）持久化狀態、檢查點、進度產物、壓縮策略
第一次跑得差不多，但結果極不穩定反饋（Loop）加外部評分器、確定性測試、有界重試
成功了也不停手，或毫無證據就宣布收工反饋（Loop）基於證據的終止狀態設計、對 Token 預算有感知的停止規則
多個專家 Agent 需要按嚴格順序協同流程（Graph）顯式定義節點、邊、路由和匯合邏輯
多步流程出錯，定位不到壞在哪一步流程加環境一起上上跟流程圖每一格對得起來的執行追蹤紀錄（Trace），而且要記得下當時的狀態
業務流還在快速迭代，需求三天兩頭改往回退用最簡單的環境層、保持純模型驅動，推遲流程的形式化

［我的整理］表格右欄有幾個詞對非工程背景的人不好懂，先在這裡換成白話：

表格裡的說法白話一點
工具契約這個工具能做什麼、要餵它什麼、會回傳什麼，有沒有寫清楚
沙箱隔離把它關在一個小房間裡做事，做壞了不會波及其他檔案
上下文注入每次開工時餵給它的背景資料，餵了什麼、有沒有餵到
持久化狀態關掉重開之後還留得住的紀錄
檢查點做到一個段落就存一次的存檔點
壓縮策略對話太長時，決定丟掉哪些、留下哪些的規則
外部評分器一個不是它自己的東西，用來打分數判斷做得對不對
確定性測試同樣的輸入一定得到同樣結果的檢查，跟 AI 的判斷無關
Schema 校驗檢查產出的格式對不對，例如該有的欄位有沒有少
節點、邊、路由、匯合流程圖上的每一格、每一條線、岔路怎麼選、幾條路在哪裡合起來

［影片作者］最後一條他特別點名「反直覺」，後面會展開。他對整張表的評價是：它把老闆和業務方那句「你們的 Agent 怎麼又抽風了」的模糊抱怨，直接翻譯成了工程師可以執行的排查工單。

［我的整理］給非工程背景的人的用法你不需要記住 Harness 這個英文字。你只要在出包的當下問自己三題：
1. 它拿得到該拿的東西嗎（資料、工具、權限、上一輪的進度）。有缺，就是環境層。
2. 它怎麼知道自己做對了、該停了。答案是「它自己說做完了」，就是反饋層。
3. 這件事真的需要固定的先後順序跟分支嗎。多數情況答案是「還不需要」，那就先別碰流程層。

七個可以直接抄的做法，我重新分成五組

［原文］以下七條的內容出自長文。［影片作者］排序是影片作者按他自己認為的落地優先級排的。

［我的整理］我把它重新分成五組。原本的一維編號會讓人以為要從第一條做到第七條，實際上它們解決的是不同類型的問題，你可以只挑自己中的那組。原始優先順序我保留在括號裡。

第一組：先把「做完」定義清楚

證據驅動的停止規則（原文金句，影片作者列為第一優先）

［原文］Agent 拍胸脯說它做完了，這話一文不值。只有測試通過、URL 連結可解析、Schema 校驗通過、或者有人工評審批准，這些硬性指標才叫真正的停止條件。

［影片作者］影片提到，做了這件事之後，「假裝完成」的事故肉眼可見地變少了。

［我的整理］白話版派工的時候就寫死「什麼東西出現才算做完」，而且那個東西要是機器或人看得見的實體。「檔案存在而且不是 0 bytes」「連結點得開」「數字加總對得上」都算。「它回報完成」不算。
延伸閱讀：AI 回報完成，實際上沒做，我遇過一次
  • AI 寫的東西我怎麼確認它是對的？抓到 AI 偷懶之後，我把它寫進流程規則　這一段講的「證據驅動停止」是原則，那篇是實際踩到的紀錄：我叫一個模型去請另一個模型修文，它沒真的叫，卻回了一版看起來像完成的答案。那篇附了可以直接複製的追問句。

有界重試（原文第二條）

［原文］光寫一句「失敗了繼續試」，絕對不能當成循環的規格。每一個循環必須寫清楚四件事：可測量的目標、每輪必須拿到的新證據、最大重試次數、以及具名的兜底路徑。

［原文］無界重試最大的惡果就一個：成本黑洞。［影片作者］影片作者補了一句：Token 帳單才是最誠實的報警器。

［我的整理］四件事裡最容易漏的是「每輪必須拿到的新證據」。少了這條，Agent 會用同樣的方式重試二十次，每次都失敗在同一個地方。有了這條，第二輪拿不出新東西就該停。

第二組：別讓它自己當裁判

確定性檢查永遠優先於模型自評（原文第五條）

［原文］讓同一個模型既當選手又當裁判、沒有任何外部防護，是長文列出的「五個最昂貴錯誤」之一。理由是自審存在嚴重的共同盲區：它寫程式時在哪裡瞎了，評審時往往還在同一個地方瞎。

［原文］能用自動化測試、Schema 校驗、程式碼 Diff 解決的，就千萬別用另一個 LLM 去評審。實在必須用大模型做評審的，一定要做上下文分離；如果是高危動作，必須上人工審批。

［影片作者］影片作者在這裡類比 TDD（測試驅動開發，一種先寫好檢查再寫東西的做法）：必須按照紅燈報錯、綠燈通過、最後再重構的單向閉環推進，不能本末倒置。

［我的整理］上面出現了兩個詞先解釋：上下文分離是指審查的那一方不要看到寫的時候的過程與理由，只看成品，免得被說服；高危動作指刪除、覆寫、對外送出、花錢這類做錯了救不回來的事。

［我的整理］日常版本：叫 AI 檢查自己剛寫完的東西，它很容易漏掉同一類問題，因為寫的時候沒想到的地方，檢查的時候通常也想不到。要嘛換一個沒看過前文的視角來查，要嘛用機器可以驗的方式查（跑一次、開一次、對一次數字）。

延伸閱讀：換一家模型來審，具體怎麼跑
  • 如何讓兩個不同的 AI 互相挑錯、自己訂正？我的企劃送出前先被模擬評審打了 2/5 分　「別讓它自己當裁判」的具體做法：兩個不同家的 AI 同輸入各自獨立寫完、互相挑錯、整合留決策點。那篇附了兩段可直接複製的提示詞。

第三組：把工作環境收乾淨

最小權限（原文第三條）

［原文］在環境層，權限、網路隔離、白名單、API 密鑰處理和人工授權，一樣都別省。權限給得太寬，被注入攻擊或者搞崩系統只是時間問題。

工具給得寧窄勿寬（原文第七條）

［原文］長文有一句話說得很重：別把 Harness 當垃圾場。塞進去的工具一多，選擇的錯誤率直線上升，上下文變得極其嘈雜，模型反而更困惑。更多的工具和記憶，絕不會自動等價於更好的結果。

［我的整理］這兩條放在一起看更清楚很多人排障的直覺是「再多給它一點東西」：多給工具、多給記憶、多給權限。長文的判斷剛好相反，給得越多，出錯機率越高。遇到 Agent 亂調用工具，先想的應該是拿掉幾個。

第四組：讓下一次接得上

用進度檔加上 Git 歷史做持久化（原文第四條）

［原文］這條經驗主要來自 Anthropic 在多會話程式碼生成上的踩坑記錄。光靠上下文壓縮根本不夠，你還需要初始化器、結構化的進度檔、Git 提交歷史，以及嚴格的增量工作紀律。目標是讓每一個新啟動的上下文，都能一眼讀懂之前到底發生了什麼。

［我的整理］不寫程式的版本：把「這件事做到哪裡」寫成一個檔案，不要只留在對話裡。對話換一個視窗就接不上，檔案比較容易交接。下一輪開場先讀那個檔案。

［我的整理］最小可用的進度檔就五個欄位，用純文字就行：

任務：（一句話講清楚要完成什麼） 完成證據：（什麼東西出現才算做完） 已完成：（條列，寫做了什麼、產出在哪） 未完成：（條列，剩下什麼） 下一步：（下一輪開工第一件事）

「完成證據」那欄就是前面第一組講的停止規則，寫在這裡等於每次開工都重讀一次。

第五組：先看真實路徑，再固化

先跑 Trace，再去畫 Graph（原文第六條）

［原文］業務都還沒跑通就急著去搞複雜的圖編排，高居長文「最昂貴錯誤清單」的榜首。正確的姿勢是：先用最簡單的環境層跑跑看，收集真實運行的執行追蹤紀錄，看看系統真正穩定的執行路徑到底長什麼樣，然後再去用圖把這套流程固化下來。

［影片作者］他對這七條的總結：沒有任何一條需要你去買新框架，全是扎扎實實的工程紀律。

三個要繞開的坑，其中一個是別太早畫流程圖

［影片作者］這一段影片作者定位為「潑冷水時間」。三個坑是他提出的警戒，其中第一個有長文作者與 AutoGen 文件佐證。

坑一：流程層的過早儀式化

［原文］長文作者自己就提醒了：如果你的任務只是給一個 Agent 三個工具讓它幹活，那強行上圖只會過早地凍結假設，讓整個系統變得無比脆弱。

［原文］圖架構真正發揮價值的場景非常明確：實質性的條件分支、並發執行、多級審批、錯誤恢復路徑，以及多專家 Agent 的協同。

［影片作者］他自己另外引了 AutoGen 文件的說法佐證：只有在需要精確控制執行順序、不同結果需要走向不同分支、或者帶複雜循環的時候，才需要用圖。（這句是影片作者引的，不是那篇長文的內容。）

［影片作者］在需求還處在「三天一改」的早期階段，過早畫圖等於作繭自縛。這也印證了對照表最後那句「往回退」。

坑二：術語包裝的嚴重通膨

［影片作者］Prompt、Context、Harness、Loop、Graph 這些詞近兩年接連走紅。影片作者的判斷是：它們確實指向不同的工程抽象層次，談不上誰搶誰的風頭，但這個圈子造新詞的速度越來越快。作為工程師要清醒，盲目追逐新名詞並不能讓系統變得更穩。

坑三：要當心「廠商敘事」

［影片作者］這篇長文大量引用了 LangChain、OpenAI Agents SDK、LangGraph、AutoGen 這些框架的說法。影片作者承認這些來源裡有乾貨，前面的判斷法和清單也確實好用，但這些資料多半出自框架或平台的維護方，難免夾帶推廣自己生態的私貨。

［影片作者］他的底線原則是：他們總結的具體工程避坑指南可以抄，但他們推銷的「複雜架構結論」必須經過自己的驗證。拿你生產環境真實的執行紀錄去驗證，別拿他們發表會上的簡報去驗證。

［我的整理］這條原則可以推廣到任何工具評估看到「你需要上更複雜的 X」這種結論，先問這句話是誰說的、他賣不賣 X。

證據停止、有界重試、最小權限，都是老規矩換了新名字

［影片作者］這是影片後段提到的一個「更隱蔽的收穫」。［我的整理］我認為對非工程背景的讀者價值最高，所以把它從結尾拉出來獨立講。

［影片作者］影片作者要觀眾回味一下這幾個詞：證據驅動停止、有界重試、最小權限原則、確定性檢查優先。然後問：是不是覺得特別眼熟。

［影片作者］他的判斷是：在傳統分散式系統、SRE 的運維手冊、網路安全規範裡，這些東西無處不在。Agent 工程發展到 2026 年，真正沉澱下來的好東西，一大半其實都是過去的老工程紀律換了一身時髦的衣服。他說這對開發者是天大的好消息，過去十年敲程式、排雷攢下的工程直覺一點都沒作廢，正在轉化成 AI 時代最堅固的護城河。

［我的整理］先接住一件事如果上面那幾個詞你一個都不熟，這段不是在說你落後。影片作者講的是他自己的工程師同溫層，那群人早就在別的地方用過同一套規矩。對其他人來說，這段的用處是反過來的，它告訴你這些東西沒有想像中新，你不必從零學起。

［我的整理］再往外推一層。如果這些紀律的本質是「先定義驗收標準、限制權限範圍、留下可追查的紀錄、失敗要有上限」，那它就不只屬於工程師。做過專案管理、做過稽核、帶過團隊、管過流程的人，手上都有同一套直覺。差別只在你以前把它用在人身上，現在要把它用在一個跑得很快、又不會自己喊停的東西上。

影片作者的三個預測，這一段是預測不是事實

先標清楚以下三條明確是影片作者對趨勢的判斷，不是長文內容，也不是已經發生的事實。他自己說「大家兩年後可以回來挖墳驗證」。
  1. 環境層的標準化會繼續加速。工具協議、權限模型、執行紀錄格式這些東西正在迅速變成公共基礎設施，自己造輪子的差異化空間會越來越小。
  2. 反饋層的核心競爭點會集中在「證據系統」。誰的自動化評分器做得更便宜、更準、更快，誰的循環就敢多跑幾輪。他附帶一個推論：測試工程的含金量會重新飆升。
  3. 流程層必將經歷一輪去泡沫化。現在那些跟風一股腦全上圖架構的專案，有一部分注定會退回到簡單的環境層。最終能留下來的，只有那些真正存在複雜分支、並行、審批和恢復剛需的重型系統。

［影片作者］他也預期新名詞還會繼續換，包裝通膨一時半會兒停不下來，但「症狀到分層」的排障邏輯，絕對比那些轉瞬即逝的術語更長壽。

一句收尾原則：迴圈只加在失敗成本高過驗證成本的地方

［影片作者］影片最後留的提醒：循環只應該加在「失敗成本遠高於驗證成本」的地方。而在其餘的任何位置，最簡單的架構就是最正確的架構。

［我的整理］這句話可以當成門檻用做一次驗證要花五分鐘，做錯一次要賠三天，那就值得加自動重試和評分器。反過來，驗證比失敗還貴的地方，加了只是多養一個會壞的東西。
延伸閱讀：真的要讓它連續跑，護欄長什麼樣
  • AI 一直停下來要授權，怎麼讓它順順跑完？迴圈護欄的五條規則　這一段說的是「什麼時候值得加迴圈」，那篇說的是「決定要加之後，護欄怎麼設」：未抗辯假設、三視角抗辯、換路煞車、驗收證據分級。

你今天就能用的排障清單：先問三題，再定位，再修

［我的整理］這份清單是我根據影片內容重組的，原始症狀對照關係出自長文。可以直接複製去用。

第 0 步：三題快篩

問題答案指向
它拿得到該拿的東西嗎（資料、工具、權限、上一輪進度）有缺，看環境層
它怎麼知道自己做對了、該停了只靠它自己說，看反饋層
這件事真的需要固定順序與分支嗎答「還不確定」，先不要碰流程層

第 1 步：對症狀，定位到層

你看到的狀況去哪一層
拿不到資料、調不動工具、權限報錯環境
換一輪對話就忘記做到哪環境
同樣的指令跑兩次結果差很多反饋
說做完了但東西是壞的反饋
停不下來，一直重試燒錢反饋
多個角色要按嚴格順序接力流程
多步流程壞了但找不到壞在哪一步流程加環境，而且要有可追蹤紀錄
需求還在三天兩頭改往回退，先別畫流程圖

第 2 步：照層別修，順序固定

環境層，先修這裡
  • 工具清單砍到只剩這次真的會用到的
  • 權限收到最小範圍，網路、金鑰、白名單一項都別省
  • 開一個進度檔記錄「做到哪、下一步是什麼」，不要只留在對話裡
  • 確認新的一輪開場讀得到那個進度檔
反饋層，再修這裡
  • 寫下這次任務的完成證據：什麼檔案存在、什麼連結打得開、什麼數字對得上
  • 設最大重試次數，並寫下超過次數要走哪條備援路徑
  • 規定每一輪必須交出新證據，交不出就停
  • 驗收改由機器或人來做，不採信它自己的完成回報
  • 真要用 AI 評審時，換一個沒看過前文的視角；高風險動作改人工審批
流程層，最後才碰
  • 預設先不做
  • 先用最簡單的方式跑幾輪，把實際走過的路徑記下來
  • 確認真的出現這四種需求才畫圖：實質分支、並行執行、多級審批、錯誤恢復
  • 需求還在頻繁改動的階段，停在這裡

第 3 步：收工前自問

  • 這一層我修好的證據是什麼（要說得出具體的東西，不是「感覺穩了」）
  • 這次的失敗成本，真的高於我加上去的驗證成本嗎
  • 我有沒有在用複雜架構去修一個環境層的小問題
