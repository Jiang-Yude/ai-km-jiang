AI 工作流 / 多裝置協作

在家裡桌機上用 Codex 做好網頁後，出門用筆電想要改，就找不到檔案了？問題出在你把專案放錯地方

發佈 2026-07-11 ｜ 最後更新 2026-07-12

兩台電腦、每台各跑兩個 AI 助手，四個環境碰同一個專案，靠 iCloud 同步注定打架。這是一次真實搬家紀錄：把網頁專案從 iCloud 遷進 git，一小時完工，附完整步驟和可以直接抄的提示詞。

這篇在講什麼

筆電做到一半的網頁，回到桌機接手，檔案不是舊的就是壞的；桌機做好的，出門用筆電想改，甚至根本找不到。如果你跟我一樣，兩台電腦、每台各跑 Claude Code 和 Codex 兩個 AI 助手，等於四個環境在碰同一個專案，這種事幾乎注定發生。這篇記錄我怎麼在一個晚上把網頁專案從 iCloud 搬進 git，讓四個環境共用同一份真相。整個搬家過程你不用自己打 git 指令，下對指令讓 AI 做就好。

適合誰
  • 有兩台以上電腦，出門筆電、在家桌機，檔案靠 iCloud 或 Google Drive 同步的人
  • 已經在用 Claude Code、Codex 這類 AI 助手做網頁或小專案，開始遇到「昨天明明改好了」的人
  • 不寫程式，聽過 git 但一直覺得那是工程師的東西的知識工作者
你會得到什麼
  • 一個判斷原則：什麼東西適合放 iCloud，什麼東西一定要進 git
  • 一套照做就能完成的搬家流程，含驗收方法
  • 「規則要寫在哪裡，每個 AI 才都看得到」的三層做法，多 AI 環境都適用

趕時間？直接跳到「你可以怎麼開始」，先把提示詞拿走。

真實現場

我平常做網頁，桌機上是 Codex 和 Claude Code 輪流上陣，筆電上也各有一套。2026 年 7 月 11 日晚上，我跟桌機的 Claude Code 說了一個困擾很久的問題：我出門的時候用筆電做網頁，回家想用桌機接手，常常出問題。反過來也一樣，桌機做好的網頁，出門想用筆電改個小地方，也會出問題。

盤點下來，我的工作環境長這樣：桌機和筆電各一台，每台上面跑 Claude Code 和 Codex，總共四個 AI 環境。專案檔案放在 iCloud 的知識庫裡，想說 iCloud 會自動同步，兩台電腦都看得到。

聽起來很合理，對吧？我也這樣覺得，直到當天晚上發生一件很妙的事。

兩分鐘的時間差 桌機的 AI 把搬家交接檔寫好存進 iCloud，我請筆電的 AI 去讀。筆電找了兩分鐘，回報：檔案還沒同步下來，連資料夾都還不存在。桌機是 22 點 28 分存的檔，筆電 22 點 30 分去找，找不到。

文件晚兩分鐘到，等一下就好。換成程式碼，這兩分鐘裡我在筆電上繼續改，改的是舊版本，兩邊就此分岔，之後不管誰蓋掉誰，都是白工。

問題來源

拆開來看，壞在三個地方。

一、iCloud 的同步是為文件設計的

iCloud 同步有三個特性，放文件沒事，放程式碼就出事：

同步有延遲

上面那個兩分鐘的現場就是證據。文件等得起，程式碼等不起，因為你不知道自己正在改的是不是最新版。

衝突處理很安靜

兩台電腦都改過同一個檔案，iCloud 常常默默生出「檔名 2」這種衝突副本，或只留下其中一邊；就算跳出提示，也不會告訴你兩邊到底差在哪。

檔案會被「瘦身」

iCloud 為了省空間，會把久沒開的檔案變成雲端佔位符。人看資料夾好好的，預期檔案已在本機的工具，一讀到還沒下載完的佔位檔就可能失敗或逾時。我同一天稍早才處理過另一個案例：一個排程工具放在 iCloud，被佔位檔搞到連線逾時，最後也是搬離 iCloud 才解決。

二、四個 AI 環境，記憶不相通

這是多 AI 工作者特有的問題。先看我說的四個環境是哪四個：

Claude Code Codex
桌機 環境 ①，一份自己的記憶 環境 ②，一份自己的記憶
筆電 環境 ③，一份自己的記憶 環境 ④，一份自己的記憶

四格，四份記憶，互不相通。桌機的 Claude Code 有自己的記憶，筆電的 Claude Code 有另一份，Codex 則完全讀不到 Claude 的記憶。我在桌機跟一個 AI 講好的規矩，其他三個環境一無所知。

所以就算搬家搬對了，只要「新家在哪裡」這個資訊只存在某一個 AI 的私有記憶裡，其他三個環境還是會照舊路徑跑去改舊檔案。

三、舊路徑會殘留在各種文件裡

我的知識庫裡有索引頁、操作手冊，裡面寫著「源碼在某某資料夾」。搬家之後這些句子全部變成地雷，哪個 AI 讀到就會被帶去錯的地方。

機制解法

核心原則：文件走 iCloud，程式碼走 git

判斷方式很簡單。問自己一句話：這個東西壞掉一小段，我看得出來嗎？

DOCUMENT · iCloud 文件：iCloud 雙向猜拳

文章、筆記、會議記錄。晚兩分鐘同步、偶爾出現一個衝突副本，人眼一看就知道怎麼處理。放 iCloud 沒問題。

CODE · git 程式碼：git 中央對帳

網頁專案、腳本、設定檔。改錯一行就整個壞掉，而且壞得很安靜。git 的工作方式是對帳：動工前先跟中央對一次帳（pull），收工後把帳回報（push）。兩邊真的改了同一個地方，它會明確告訴你衝突在哪，讓你選；只要有提交過（commit），兩邊的內容都找得回來。

搬家流程（當晚實際走過的版本）

STEP 1 盤點

先列出所有網頁專案在哪裡、哪些還活著、哪些已經是歷史。我讓 AI 掃了整個知識庫，找出還住在 iCloud 的活躍專案。

STEP 2 複製，先不刪

把專案複製到本機的 Developer 資料夾，建立 git repo，跟原檔比對確認一致。原資料夾原封不動留著，這是後悔藥。

STEP 3 推上 GitHub 私有 repo

私有的意思是源碼只有你看得到；網站本來就是部署出去給人看的，訪客完全不受影響。

STEP 4 在舊資料夾掛門牌

留一個說明檔在原位置，寫清楚「本資料夾已凍結，真相在某某 repo，改這裡無效」。誰路過舊家都會被引導去新家。

STEP 5 更新所有舊路徑

索引頁、操作手冊裡寫著舊位置的句子，一個一個改成新位置，不留地雷。

STEP 6 筆電 clone，雙機驗收

筆電寫一行測試、推上去；桌機拉下來看到、刪掉、推回去。一圈走完，代表同步鏈是通的。

當晚實測，整條流程走完不到一小時，雙機驗收一次通過。

規則要寫在哪裡：三層

多 AI 環境的關鍵一課：規則的效力範圍，取決於它寫在哪裡。

全域規則檔

所有 AI 都會先讀的規則主檔。「程式碼一律 git、放本機 Developer」這條寫在這裡，四個環境都吃得到。

門牌卡

跟著檔案走的規則，寫在舊資料夾裡。不管哪個 AI、透過什麼路徑摸到舊檔案，第一眼就看到警告。

AI 私有記憶

每個 AI 自己記的東西，只對它自己有效。方便，但千萬別把「真相在哪」這種關鍵資訊只放這一層。

寫的位置越靠近檔案本身，越不容易漏。我的順序是：先寫門牌卡，再更新全域規則，私有記憶只當快取。三層分別怎麼做：

全域規則檔在哪裡、怎麼寫 Claude Code 會自動讀專案資料夾裡的 CLAUDE.md，Codex 會自動讀 AGENTS.md。我的做法是只維護一份 AGENTS.md，放在兩台電腦都同步得到的知識庫根目錄（規則檔是文件，走 iCloud 同步沒問題），CLAUDE.md 只留一行「先讀 AGENTS.md」。內容用白話條列就好，例如：「網頁專案一律放 ~/Developer/、用 git 管理；開工先 git pull，收工必 git push。」一份規則，四個環境都吃得到。
門牌卡是什麼 一個普通的說明檔，放在搬家後的舊資料夾裡，檔名取醒目一點，我用「⚠️ 門牌：本資料夾已遷移」。內容三句話：本資料夾已凍結，不要改；源碼真相在哪個 repo；要接手就 git clone 哪裡。它守的是最後一關：不管哪個 AI、還是三個月後已經忘記這件事的你，循舊路徑摸進來，第一眼就被引導去新家。
AI 私有記憶怎麼管理 你在對話裡叫 AI「記住」的東西，只存在那台機器的那個工具裡，換一台電腦、換一個 AI 都讀不到。管理原則就一條：私有記憶只當快取。對話中發現一條值得跨環境通用的規矩，當場升級寫進全域規則檔；跟特定資料夾綁定的資訊，寫成門牌卡。讓檔案和規則檔當真相，記憶只負責加速。

之後的日常：一條規矩

開工先 pull，收工必 push 就這一條。出門用筆電：pull、改、push。回家用桌機：pull、接著做。哪台機器、哪個 AI 都一樣。我還請 AI 準備了一個每晚十點的檢查任務，看有沒有改了忘記推的，有就提醒我。

它保證什麼、不保證什麼

保證的部分：只要照著「開工 pull、收工 push」走，iCloud 那種「默默蓋掉、默默分岔」的無聲事故就不再發生。git 把每一次提交都記了帳，就算真的衝突，它會把衝突攤在你面前讓你選；有提交過的內容，都找得回來。

誠實邊界 它治不了忘記 push。筆電改完沒推，回家桌機還是看不到，這是紀律問題，工具只能提醒。另外，搬家當下所有寫著舊路徑的文件都要更新，漏一份就是一顆地雷，我自己也還有兩份排在待辦清單上，靠門牌卡先擋著。

你可以怎麼開始

最小可行的第一步，是讓你的 AI 幫你盤點。把這段丟給你的 Claude Code 或 Codex：

# 可以直接複製的盤點提示詞 我的專案檔案放在 iCloud（或 Google Drive）同步資料夾裡， 我有多台電腦會輪流編輯。請幫我： 1. 盤點同步資料夾裡所有的程式碼類專案（網頁、腳本、設定檔） 2. 列出每個專案：位置、是否活躍、有沒有 git 3. 給我一份搬遷建議清單：哪些該遷入 git repo、哪些可以不動 只盤點，先不要動任何檔案。

盤點完，挑一個最活躍的專案先搬。搬家也讓 AI 做，一次搬一個：

# 搬家執行提示詞（一次搬一個專案） 請把 [專案資料夾路徑] 遷入 git 管理： 1. 複製到 ~/Developer/[專案名]/，先不要動原資料夾 2. git init、首次 commit，跟原檔 diff 確認內容一致 3. 建 GitHub 私有 repo 並推上去（建立前先跟我確認） 4. 在原資料夾留一個門牌說明檔：已凍結、真相在哪個 repo 5. 列出所有寫著舊路徑的筆記或文件，先給我清單，我確認後再改 全程不刪除任何檔案，每一步回報結果。

跑通驗收再放大到其他專案。搬完之後記得三件事：舊資料夾掛門牌、全域規則補一條、所有寫著舊路徑的文件更新掉。

收尾 Recap

  1. 兩台電腦四個 AI 碰同一個專案，靠 iCloud 同步注定打架，因為它的同步是為文件設計的。
  2. 判斷原則一句話：壞掉一小段人眼看不出來的東西，交給 git。
  3. 搬家六步：盤點、複製不刪、推私有 repo、掛門牌、更新舊路徑、雙機驗收。
  4. 規則寫在哪決定誰看得到：全域規則檔給所有 AI、門牌卡跟著檔案走、私有記憶只當快取。
  5. 日常一條規矩：開工先 pull，收工必 push。

常見的坑（與對策）

搬家後直接刪舊資料夾先凍結掛門牌，用一週確認新流程順了再清，清也是進垃圾桶不直接刪。
只搬檔案，不更新規則四個環境裡只要有一個還記得舊路徑，它就會回去改舊檔案。搬家和改規則是同一件事的兩半。
把部署和同步混為一談git 管的是你和你的機器之間的同步；網站部署照原本的流程走，兩件事互不干擾。
圖快用「小改直接動 iCloud 那份」平行真相都是這樣長出來的，再小的改動也走 repo。

給自己的定位提醒

這篇解的問題很技術，但核心跟我一直講的事情一樣：AI 再聰明，也需要你把環境架好。四個 AI 環境不打架，靠的是一份大家都讀得到的規則、一個唯一的真相位置，和一條簡單到不會忘的紀律。把地基架好，AI 才能真的幫你累積，而且是四個一起幫你累積。
