AI 工作流 / 多 AI 並行

兩個 AI 一起加資料，為什麼總是撞在同一個檔？｜把大檔拆成一單位一檔，讓它們不用排隊

前一篇把共用的桌子拆成一人一桌，施工期不排隊了。可是合併上線時，還有一份大家都要改的總清單，每次都撞。這篇把那份清單也拆掉：一篇一檔，清單由機器算出來。

這篇在講什麼：我的官網有一份 135 篇文章的總清單檔，每篇文章上線都要往裡面加一筆。多個 AI 分頭寫文章時，別的檔都不撞，就這一個檔每次都撞。這篇講我怎麼把它拆成「一篇文章一個小檔」，讓清單檔變成機器算出來的生成檔，兩張桌子同時上線也不用互等。中段攤開另一家 AI 三輪審稿抓出的八個洞，最後給你判斷自己手上哪個檔該拆的三個問題、生成器的最小骨架，和一段可以直接貼給 AI 的委託指令。

適合誰
  • 已經讓兩個以上的 AI 幫你維護一個網站、一份目錄或一張清單，發現它們常常在同一個檔案上互相蓋掉的人
  • 讀過前一篇〈兩個 AI 同時改一個網站，為什麼會打架？〉、裝了分軌施工，卻發現合併時還是有一個檔每次都要人工解衝突的人
  • 幫客戶或團隊設計「多人一起加資料」流程的人，想知道哪種檔案天生會變成瓶頸
你可以帶走什麼
  • 三個問題，判斷你手上哪個檔案是「共享熱點」
  • 一個生成器的最小骨架：讀一堆小檔、驗證、排序、輸出，附四種模式
  • 「三方漂移判定」的一句話版，讓生成檔被人手改時機器抓得到，又不會誤傷正常改動

前情：掛牌講好了誰等誰，沒解掉為什麼要等

前一篇〈兩個 AI 同時改一個網站，為什麼會打架？〉講的是把共用的一張桌子拆成一人一桌（git worktree），上線時走一支合併腳本。裝完之後，施工期真的不排隊了。

但我在 9 月 5 日做「圖譜工程 v2」的雙軌分析時，讓 Claude 與 Codex 各自獨立看整套流程，兩邊不約而同指到同一個檔：articles-data.js。

它是官網深度文章的總清單，瀏覽器靠它畫出文章總覽，也靠它畫出每篇文章底下的相關文章。135 篇文章的標題、摘要、標籤、關聯全寫在裡面，單檔 188,593 bytes。每篇新文章上線，都要往裡面加一筆。

於是它成了唯一「每次都撞」的地方。兩張桌子各寫各的文章，其他檔案完全不相干；只有合併進主線時，兩邊都在這個檔的同一個位置加了一行，Git 一定報衝突。我們原本的對策是把它列進「共享熱點」清單：開桌時登記、合併時人工看一眼。

登記制講清楚了誰先誰後。可是只要這個檔還在，排隊就永遠在。

關鍵判斷掛牌是「講好誰等誰」，拆檔是「讓人不用等」。前者是規則，後者是結構。規則要人記得遵守，結構不用。

技術面：一單位一檔，清單變成算出來的

做法一句話：清單檔不再由人維護，改由機器從一堆小檔算出來。

拆法

每篇文章的資料，搬進文章自己的資料夾，叫 article.json：

articles/ parallel-site-editing/ index.html 文章本體（原本就在） article.json 這篇的標題、摘要、標籤、關聯（新增） publish-gate/ index.html article.json ... articles-tags.json 受控標籤清單（哪些標籤可以用） articles-data.js 生成檔，機器算出來，不要手改

一篇 article.json 長這樣：

{ "id": "split-shared-hotspot", "url": "articles/split-shared-hotspot/", "date": "2026-09-06", "title": "兩個 AI 一起加資料，為什麼總是撞在同一個檔？", "summary": "……", "tags": { "topic": ["AI工作流"], "level": ["進階"], "content_type": ["教學文章"] }, "related": ["parallel-site-editing", "publish-gate"] }

寫新文章的人，只動自己資料夾裡的兩個檔。兩張桌子同時上線，各自新增的是不同資料夾裡的不同檔案，Git 沒有東西可以衝突。

生成器做四件事

一支腳本 build-articles-data.mjs，讀所有 article.json，然後：

  1. 驗證：id 要等於資料夾名、url 要等於 articles/<id>/、日期格式、related 指到的 id 必須存在、id 不能重複、不認識的欄位直接報錯。
  2. 排序：依（updated 或 date）新到舊，同日再依 date、再依 id。
  3. 輸出：寫成跟舊手寫版一模一樣格式的 articles-data.js。
  4. 守門：發現有人照舊習慣直接手改了生成檔，停下來列出是哪幾筆，不靜默覆蓋。

第 3 點值得多說一句。官網另外有三支腳本用正規表達式（regex）直接讀這個檔的文字，沒有用 JavaScript 載入。只要輸出格式跟舊版一個字元都不差，那三支腳本一行都不用改。實測 135 篇逐筆比對內容相同，三支腳本對新舊檔的解析結果相同。改一個東西的時候，讓吃它的人完全無感，是拆檔能不能安全上線的關鍵。

四種模式

指令做什麼誰用
不帶參數重建；偵測到手改就停本機預覽
--check只比對不寫，不一致就回失敗上線前檢查（preflight）
--adopt把手改的那幾筆回寫成 article.json，再重建遷移舊分支、救援
--force丟掉手改直接重建確定要丟才用

合併時統一重建

上線用的合併腳本多了一段：先合併分支，重跑生成器，再把重建結果跟文章壓成同一個 commit 推出去。如果合併時 articles-data.js 本身報衝突（例如某張舊桌子照舊習慣手改了它），腳本先收下分支那一版，再交給生成器判定；另外三個生成檔（站內索引、關鍵詞、英文清單）直接收主線版然後重建。

邊界：只有這四個生成檔會自動收sitemap.xml 與 llms.txt 這兩個給搜尋引擎和 AI 讀的檔，目前還是人手維護，撞到還是人工解。它們沒拆的理由在決策面那一節。

系統面：另一家 AI 三輪審稿抓出的八個洞

機制是我和 Claude 一起寫的。寫完沒有直接上，丟給 Codex（OpenAI 那家）用唯讀模式審，同一個審稿對話連續三輪，每輪修完再回去。三輪各抓到什麼，我照原樣列出來，因為這比機制本身更有教學價值。

第一輪：三條，NEEDS_REVISION

洞一：兩方比對會誤傷正常改動我原本的守門邏輯是「生成檔裡有一筆跟來源不一樣，就是有人手改」。Codex 指出：某張桌子只改了自己的 article.json、還沒重跑生成器，這時生成檔當然跟來源不一樣，但那只是「過期」，重建即可。兩方比對分不出「過期」跟「手改」，會把正常的工作流擋下來。
洞二：--adopt 回寫前沒驗證手改的那筆如果 url 寫錯，回寫時會蓋到別篇文章的 article.json。修法：回寫前要求 url 必須等於 articles/<id>/、跑完整驗證、目標檔若屬於別的 id 直接拒絕。
洞三：衝突一律收主線版，會讓分支上的手改在重建前就消失修法：articles-data.js 的衝突改收分支版，再交給生成器判定。該判斷「這是手改還是過期」的是生成器，合併腳本不該先替它決定。

另外兩點屬於提醒：排序會改變，要先告訴站主（決策面那節講）；不宜自動上線，要站主授權（本來就是這樣設計的）。

第二輪：三條，NEEDS_REVISION

洞一修成「三方判定」之後，Codex 再看，說方向對了，但基準版取錯。

洞四：合併之後的「基準版」已經不是分叉點三方判定需要一個基準：分支是從主線的哪個時間點分出去的。我用「目前主線與遠端的共同祖先」當基準，但合併腳本用的是 squash merge，做完之後這個共同祖先就是主線自己，不是分叉點。主線如果在分支分出去之後更新過某篇文章，就會被誤報成漂移。修法：合併腳本在 squash 之前先算出分叉點，連同主線當下的版本，用環境變數傳給生成器。

這一點我要說準：基準版是合併腳本算好傳進來的。生成器自己在工作桌上跑時，只用「與遠端主線的共同祖先」當基準；沒有遠端就退回目前版本；不在 git 裡就退回兩方比對並印出警告。它沒有「自動知道分叉點」的能力。

洞五：刪掉 article.json 會讓文章無聲退出索引生成器只看有哪些 article.json，少一個就當來源更新了，那篇文章從總覽消失，沒有任何錯誤訊息。修法：有 index.html 卻沒有 article.json 的資料夾直接報錯；真的要刻意不進索引，放一個空檔 article.unlisted 明示意圖。

這跟 .vercelignore 是兩種不同的意圖：article.unlisted 是「頁面上線，但不進清單」；.vercelignore 擋著的資料夾是「整個不上線」，生成器對後者是自動略過並印出來，讓索引不會宣告一個不存在的頁面。

洞六：標籤清單沒做三方判定，回寫時也沒驗受控標籤清單 articles-tags.json 也可能被人合法修改，同樣要三方判定；--adopt 回寫標籤前要驗證。補上。

第二輪 Codex 同時改了一個判斷：前一篇文章立的鐵則「分支禁止提交生成檔」，在三方判定之下可以放寬成「允許提交，機器會判」。這是機制成熟的訊號：原本要靠人記得的規則，變成機器能處理的情況。

第三輪：兩條小修，APPROVED_WITH_CONDITIONS

洞七：讀標籤清單時，拼錯的頂層欄位會被靜默省略改成不認識的欄位直接報錯。
洞八：非生成檔衝突時腳本會退出，環境變數跟著消失這時人要手動續跑生成器，提示訊息必須教人自己把分叉點帶進去，否則續跑的那一次就退回錯誤的基準版。

第三輪的結論原文：「允許分支提交 articles-data.js 現在可接受，正常 squash 衝突未見靜默丟資料路徑。」附一個條件：取得站主排序確認再上線。

三方漂移判定，一句話版

一句話記住生成檔裡的一筆，既不等於來源，也不等於任何一個基準版，才算有人手改。等於來源＝已同步；等於基準版＝只是過期，重建即可。

每輪修完怎麼驗

每一輪修完，我都在一個暫存的 git 倉庫（含假的遠端）重跑一組情境，不只看程式碼：

  • 改既有 article.json、不重建：要放行
  • 舊式直接往生成檔 append：要擋
  • 分支 commit 了手改過的生成檔：要擋
  • 主線更新過某篇、分支帶著舊版：只用主線當基準會誤報，帶分叉點後要放行，且取主線的新值
  • 刪 article.json：要擋；放 article.unlisted：要放行
  • 改標籤清單、不重建：要放行；手改生成檔裡的標籤：要擋
  • --adopt 的 url 指到別篇：要拒絕，且對方檔案一個字不能動

還模擬了兩張桌子同時上線：各加一篇、各自重建，第二桌合併時只撞 articles-data.js，腳本自動處理後兩篇都在。

決策面：順序回不去、哪些檔該拆、哪些還沒收尾

一個回不了頭的決定：順序

舊清單的順序是這幾個月手工 prepend 與 append 混出來的，沒有任何規則能從資料重建它。生成器必須選一個確定的排序，我選了跟總覽頁顯示邏輯一致的：更新日或發布日新到舊。代價是同一天發的文章，彼此的相對位置會變：135 個位置裡有 67 個換位，全部是同日之內互換。

Codex 第一輪就點出這會連動總覽頁、相關文章的同分推薦、站內搜尋與 AI 客服的編號，要先告訴站主。所以合併之前，我先確認過訪客看得到的差別只有這一項，拍板才推。

拆檔前先找的東西這類「無法從資料重建的隱性狀態」，拆檔前一定要先找出來。它不會報錯，只會在上線後讓人覺得順序怪怪的。

三個問題，判斷哪個檔是共享熱點

問題 1每新增一筆，都要動它嗎？

目錄、索引、總表、清單，通常是。

問題 2兩個以上的人或 AI 會同時加嗎？

只有你一個人加，它就只是大檔，還算不上熱點。

問題 3它能不能從別的東西算出來？

算得出來的就該變成生成檔；算不出來的（例如人工排的精選順序）要另想辦法。

三個都是「是」，就拆。

沒拆的兩個檔，和一份還沒改的清單

sitemap.xml 與 llms.txt 也符合前兩個問題，這次我刻意沒拆。原因有兩個：這一輪的範圍是解掉「每次都撞」的那一個，它們撞的頻率低得多；而且 llms.txt 每一筆的摘要是寫給 AI 讀的，我還想保留人工寫的空間。站內搜尋的別名檔 search-aliases.js 是下一個候選，同一招可用。

另外誠實說兩件還沒收尾的事。第一，登記簿的共享熱點清單（hotzones.json）到現在還列著 articles-data.js。功能上已經沒有影響，因為不再有人需要登記它，但清單本身還沒改，等 9 月 19 日的復盤一併整理。第二，既有文章有 17 處主題標籤不在受控清單裡，生成器只提醒、不擋；要不要把那些詞納入清單是內容決定，還在我手上。

這套做法不新

一篇一檔、機器合併成清單，是靜態網站產生器（Jekyll、Hugo 這類）早就在做的事，每篇文章頂端的 front matter 就是這裡的 article.json。我做得晚，是因為網站起步時只有一個 AI 在維護，單檔最省事。真正逼我拆的是「多個 AI 並行」這個新情況，它把原本無所謂的大檔變成了瓶頸。如果你的站一開始就用產生器架，拆檔這件事你早就有了，這篇對你的價值在三方判定與上面那三個判斷問題。

哪些事可以放心交給機器算，我用的是同一條判準
  • 哪些事可以交給 AI 自己跑完？｜我把內容產線拆成五個小迴圈　那篇的兩層判準（能不能客觀驗出對錯、錯了可不可逆）也適用在這裡：生成檔有 --check 可驗、重建即可逆，兩層都過，所以可以放心交給機器算

給你的落地做法

生成器最小骨架

讀取：掃所有 <單位資料夾>/<單位>.json，加上受控清單 驗證：id＝資料夾名、url 對得上、日期格式、關聯指到存在的 id、id 不重複、不認識的欄位報錯 排序：選一個可以從資料算出來的確定順序（不要依賴檔案系統順序） 輸出：格式跟舊清單完全一致（讓現有的讀取端無感） 守門：三方比對；有漂移就停下列出，不靜默覆蓋 模式：預設重建｜--check 只比對｜--adopt 回寫來源｜--force 丟手改

合併腳本要多做的三件事

  1. squash 之前先算分叉點，連同主線當下的版本傳給生成器。
  2. 生成檔衝突：清單檔收分支版交生成器判，其他生成檔收主線版重建；非生成檔衝突照舊停下，提示裡要教人手動帶基準版。
  3. 重建結果跟內容壓同一個 commit。

貼給 AI 的委託指令

懶得自己想的話，把這段直接貼給你的 AI：

我的網站（或清單）有一個大檔 <檔名>，每新增一筆都要改它，多個 AI 並行時每次都在這裡衝突。 請幫我： 1. 把它拆成一單位一檔：每個單位的資料放進自己的資料夾（<資料夾>/<id>/<單位>.json），受控欄位另放一份清單檔。 2. 寫一支生成器：讀所有小檔，驗證（id＝資料夾名、url 對應、日期格式、關聯 id 存在、id 不重複、未知欄位報錯），用確定的規則排序，輸出格式與舊檔完全一致。 3. 生成器要有四種模式：預設重建（偵測到手改就停）、--check 只比對、--adopt 把手改回寫成來源檔、--force 丟掉手改。 4. 手改的判定用三方比對：一筆既不等於來源、也不等於基準版（分叉點與主線當下）才算漂移。基準版由合併腳本在 squash 前算好，用環境變數傳入。 5. 有本體檔卻沒有來源檔要報錯；刻意不進清單的，用一個空的旗標檔明示。 6. 合併腳本：清單檔衝突收分支版交生成器判，其他生成檔收主線版重建，非生成檔衝突停下並提示如何手動帶基準版；重建結果與內容同一個 commit。 先在暫存倉庫用情境測試驗證（改來源不重建要放行、直接改生成檔要擋、刪來源檔要擋、兩桌同時上線兩篇都要在），再告訴我舊檔裡有哪些「無法從資料重建」的東西（例如順序）需要我拍板。

彩蛋：這篇是拆檔上線後開的第一張桌子

這篇文章的資料就寫在 articles/split-shared-hotspot/article.json，我從頭到尾沒有碰 articles-data.js。它上線時，合併腳本會自己把它算進清單。前一篇的彩蛋是「機制的第一個使用者是它自己」，這篇延續同一件事。
